# ConsultBae AI Automation Assignment

## What this is

Three messy CSVs (recruitment applicants, gig workers, CBNexus contacts) merged
into one canonical people database, plus an n8n automation that LLM-categorizes
each person's skills, plus a small web app for collecting and analyzing audio
submissions.

## Project structure

```
project/
├── data/                        # the 3 supplied CSVs
├── pipeline/
│   ├── normalize.py              # pure normalization functions (phone/email/city/name/date/ctc/rate)
│   ├── ingest.py                 # reads CSVs, repairs structural corruption, logs issues
│   ├── match.py                  # tiered entity resolution (email/phone/name+city/fuzzy)
│   └── database.py               # SQLite schema + loader (run this to (re)build the DB)
├── app/
│   ├── main.py                    # FastAPI: n8n integration endpoints + audio app
│   ├── audio_analysis.py         # ffprobe/ffmpeg-based metadata extraction
│   └── static/                   # plain HTML/JS frontend (submit + submissions list)
├── n8n/
│   └── skill_tagging_workflow.json
├── reports/
│   └── data_quality_report.md    # Task 4 deliverable
├── tests/
│   └── test_pipeline.py
├── uploads/                       # audio files land here (gitignored contents, dir kept)
├── consultbae.db                 # generated by pipeline/database.py, not hand-edited
└── requirements.txt
```

## Setup

Requires Python 3.10+ and `ffmpeg`/`ffprobe` on PATH (system package, not pip).

```bash
# system dependency (Ubuntu/Debian)
sudo apt install ffmpeg
# macOS
brew install ffmpeg

pip install -r requirements.txt
```

## Running the pipeline (Task 1)

```bash
python pipeline/database.py
```

This reads the 3 CSVs from `data/`, cleans/normalizes them, resolves duplicate
people across sources, and (re)builds `consultbae.db` from scratch. Safe to
re-run any time — it's fully deterministic given the same input CSVs.

Inspect results directly:
```bash
python pipeline/match.py     # prints every merged person + match decisions
python pipeline/ingest.py    # prints structural issues found during ingest
```

Run the regression tests:
```bash
python tests/test_pipeline.py
# or: pytest tests/test_pipeline.py -v
```

## Running the app (Tasks 2 & 3)

```bash
uvicorn app.main:app --reload --port 8000
```

- `http://localhost:8000/` — submit audio (record in-browser or upload a file)
- `http://localhost:8000/submissions` — view all submissions with playback + extracted metadata
- API docs (auto-generated by FastAPI): `http://localhost:8000/docs`

The audio app tries to auto-link each submission to an existing person from
Task 1's database by normalized phone number. If no match is found, the
submission is still stored (`linked_person_id: null`) — we never block a
submission just because we can't identify the person.

## Task 2: n8n automation

See `n8n/skill_tagging_workflow.json`. Import it into n8n (self-hosted or
cloud trial). Setup steps and how to demo it are in `n8n/README.md`.

Flow: **Webhook → GET person's skills from our API → LLM categorizes into
automation-heavy / web-dev / data → parse the LLM's JSON response →
POST the result back to our API**, which writes it into the `skill_categories`
table.

We front the database with a small FastAPI layer (`app/main.py`) rather than
having n8n talk to SQLite directly, because n8n's SQLite support is a
community node with weak concurrent-write guarantees — an HTTP API is the more
standard integration pattern and matches how n8n would actually talk to a real
backend in production.

## Database design decisions

**Why SQLite, not Postgres.** The brief says "your choice." Postgres is
defensible (and pairs natively with n8n's Postgres node) but for a 48-hour
take-home that a stranger needs to clone and run with zero setup, a
single-file SQLite database removes an entire category of "doesn't run on my
machine" failure. In an interview I'd say: Postgres in production for
concurrent writes and connection pooling; SQLite is the right tool for a
single-user local demo.

**Why we don't overwrite conflicting source data.** Instead of one wide table,
we keep `people` (canonical identity) separate from `applicant_profiles`,
`gig_profiles`, `nexus_profiles` — one row per *source record*, all pointing
at the same `person_id`. When two sources disagree (e.g. two different
"Deepak Nair" gig records with different rates and cities), both rows are
kept, both visible, nothing silently picked as "correct." That's a real
design decision, not a shortcut — arbitrarily overwriting one source's data
with another's would hide information a real business would need.

**How we resolve duplicate people.** Tiered, confidence-scored matching (see
`pipeline/match.py` and the data quality report for full detail):
1. exact normalized email → merge (confidence 1.0)
2. exact normalized phone → merge (confidence 0.95)
3. exact name + exact city, no conflicting phone → merge (0.85)
4. abbreviated-initial name match ("R. Verma" ~ "Rohit Verma") + same city → merge/flag depending on confidence
5. Same name alone is **never** sufficient — see the Deepak Nair and Arjun Mehta
   cases in the data quality report, where identical names were deliberately
   *not* merged (or, in Arjun Mehta's case, actively blocked from a
   transitive false-merge).
